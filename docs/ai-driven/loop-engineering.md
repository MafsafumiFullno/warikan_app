# ループエンジニアリング運用

## 目的

AI駆動開発を単発の実装依頼ではなく、観測、仮説、変更、検証、学習の反復として運用する。

## 自走方針

ループは、ユーザー承認を最小化して自走する。承認はリスクが高い操作に限定し、観測、整理、小さな修正、検証、記録は原則としてエージェントが進める。

## 基本サイクル

1. Observe: 現状の差分、失敗、ユーザー影響、既知の制約を確認する
2. Frame: 直す対象、直さない対象、守る不変条件を明確にする
3. Act: 最小変更で実装する
4. Verify: テスト、契約、不変条件、必要ならE2Eで確認する
5. Learn: 発見したルール、未解決事項、次の改善候補を記録する

## 実装時のテストレビュー

TDDでは、実装者が作ったテストだけでGreenへ進まない。変更リスクに応じて、Spec Reviewer、Contract Reviewer、Data Reviewer、Security Reviewer、Regression Reviewer の観点を使い、テストの抜け漏れを確認してから実装する。

## ゲート

ゲートは「毎回ユーザー承認を取る場所」ではなく、「次へ進む判断基準」として扱う。低リスクで可逆な作業は、ゲート条件を満たす限り自動で進める。

### 不変条件ゲート

- `docs/domain/warikan/common-invariants.md` を正本として確認する
- `project_member_id` と DB PK の `id` を混同しない
- `del_flg = false` の前提を取得、参照、更新、削除で確認する
- Frontend の API 呼び出しは `@/lib/api` の `apiFetch` を使う

### 契約ゲート

- API の path, method, request, response, error を確認する
- backend, frontend, tests の3層で同じ意味のIDと型を使う
- 互換入力を残す場合は、内部変換とレスポンスの意味を明記する

### テストゲート

- 変更対象の最小テストを先に確認または追加する
- 正常系、異常系、境界値、権限、論理削除を必要に応じて含める
- UIや主要導線に影響する場合はE2E実行を判断する

### 学習ゲート

- 新しく見つかった設計判断は `docs/domain/` または `docs/issues/` に残す
- 一時的な仮修正はブランチ、stash、issueメモで分離する
- 次ループに持ち越す項目は「判断待ち」「実装待ち」「検証待ち」に分類する

## 承認を求める場面

- commit、push、PR作成の本実行
- main / master への直接操作
- force push、reset、rebaseなど履歴を書き換える本実行
- `.env`、シークレット、認証情報、外部サービス設定の反映
- DBマイグレーション、データ削除、破壊的なコマンドの本実行
- 仕様やUXの選択肢が複数あり、プロダクト判断が必要なとき
- 依頼範囲を超える大きなリファクタやアーキテクチャ変更

## 自動化レベル

| レベル | 扱い | 例 |
|--------|------|----|
| A: 自動実行 | 承認なしで進める | 読み取り、差分確認、lint、typecheck、対象テスト、ドキュメント整合修正 |
| B: 自動準備 | 成果物作成まで進め、本実行は止める | PR本文案、環境変数リスト、マイグレーション計画、削除対象リスト |
| C: ローカル限定実行 | ローカルで戻せる範囲だけ進める | テストDBへの migrate、ローカルDocker再起動、作業ブランチ作成、stash作成 |
| D: 承認必須 | 外部影響または復旧困難なため止める | push、PR作成、本番設定反映、force push、実データ削除 |

## 外部設定の自動化基準

- 自動でよい: 設定差分の確認、必要なキー一覧の作成、サンプル `.env.example` の更新、Render/GitHub設定案の文章化
- 承認が必要: 実際の外部サービスへの反映、Secrets登録、公開URL変更、Webhook有効化、課金や通知が発生する設定

## 破壊的操作の自動化基準

- 自動でよい: 影響範囲の確認、削除対象リスト作成、dry-run、バックアップ手順作成、テストDBでの検証
- 承認が必要: 実ファイル削除、実データ削除、履歴改変、Docker volume削除、戻せないマイグレーション適用

## 自動で進めてよい場面

- ファイル・差分・ログ・テスト結果の確認
- 体制ドキュメント、Rules、Agents、Skillsの整合修正
- 明確な誤字、リンク、パス、表記ゆれの修正
- 既存方針に沿う小さなテスト追加やドキュメント追記
- lint、typecheck、対象テストなどの非破壊な検証
- 未追跡ファイルや別件差分をステージせずに状況報告すること
- PR本文案、設定案、削除計画、マイグレーション計画などの下書きを作ること

## 自動実行時の報告

- 何を見たか
- 何を直したか
- どのゲートを通したか
- 何をユーザー判断として残したか

## 使い分け

- 新機能: `loop-engineering-lead` で対象を観測してから `spec-delivery-lead` に接続する
- 既存改修: `loop-engineering-lead` でAs-Isを固定してから `refactor-lead` に接続する
- PR前: `loop-engineering-lead` で学習ゲートまで確認してから `pr-coordinator` に接続する
